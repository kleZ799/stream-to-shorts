Choose what does the work — the GPU, the CPU, or whatever is fastest — and no
more CUDA errors. Faces are found by a better detector, and "follow my face"
renders about five times faster.

## Settings → Processor

A new choice in Settings: **Automatic**, **GPU**, or **CPU only**.

On **Automatic** (the default) the app uses the fastest thing this computer
really has:

- **Video** is encoded on the graphics chip — NVIDIA, Intel, AMD, or a Mac's —
  which roughly halves render time. Each one is given a one-second test encode
  before it is trusted, because a graphics driver can claim more than it can
  do. If one fails partway through a run, that clip is redone on the CPU and
  the rest of the run stays there.
- **Transcription** uses an NVIDIA GPU when NVIDIA's CUDA libraries are
  installed.

**CPU only** never touches a graphics chip — the switch to reach for if a
driver keeps misbehaving. The panel says in plain words what each stage is
using and why, and a change applies from the next clip, even on a paused run.

## No more CUDA errors

If you have an NVIDIA card, transcription used to start on the GPU, fail
because the download does not include NVIDIA's CUDA libraries (they are about
2 GB), and fall back to the CPU with an error that looked like the app had
broken. Now it checks for those libraries first, and if they are not there it
simply uses the CPU and says why. Video encoding still uses the GPU either way
— that needs only your graphics driver.

## Pause now pauses everything

Pause used to stop video rendering but let transcription carry on, because
transcription runs inside the app rather than as a separate program. It now
holds transcription and face tracking too, on the CPU or the GPU.

## A better face detector

Faces are now found with **YuNet**, a small learned detector from OpenCV that
ships inside the app (about 230 KB — nothing downloads). It finds faces the old
detector missed: turned heads, dim rooms, headsets. On the test streams, the
webcam overlay is now located from almost every sampled frame instead of a
handful, and the face-following crop loses the face less often. The old
detector is still there as a fallback.

## "Follow my face" is about five times faster

It turned out almost none of its slowness was face tracking. Cutting each clip
decoded the whole stream from the beginning up to the clip, instead of jumping
straight to it — so a clip half an hour into a stream paid for half an hour of
video first. Fixed: 30 seconds of a 720p stream now takes about 11 seconds on
a GPU and 17 on a CPU, down from 73 and 91. The warning that it was slow is
gone, because it no longer is.

**StreamToShorts.exe** — about 220 MB, Windows, self-contained. Unsigned, so
SmartScreen will warn: **More info → Run anyway**.

**StreamToShorts-linux-x86_64** — about 278 MB, x86-64, self-contained, glibc
2.35 or newer. `chmod +x` it and run it. **Still untested on a desktop
distribution** — every published build is started by the release workflow and
asked for its interface before the release exists, but nobody has yet sat at
Fedora and made a Short with it. Take `StreamToShorts-linux-README.txt` too.

**StreamToShorts-macOS-arm64.zip** — about 165 MB, Apple Silicon only. **Still
a beta, and still has never been run on a Mac** — I do not own one, so it is
built and checked by GitHub's macOS runners and published without a human
opening it. On a Mac, video encoding uses Apple's VideoToolbox after it passes
a test encode; transcription stays on the CPU. If it does not start, that is a
bug here: `~/Movies/StreamToShorts/app.log` and
[an issue](https://github.com/kleZ799/stream-to-shorts/issues/new) are how it
gets fixed.

On v1.5.0 or later on Windows, or on any Linux build? The app will offer this
to you.
