Updating no longer leaves a spare copy of the app on your disk.

## The fix

v1.5.1 updated itself correctly but left a full-size duplicate of the new build sitting next to it — a 219 MB file that served no purpose and, combined with the build it replaced, could strand well over 400 MB after a single update.

The staged download is supposed to stop existing the moment it becomes the new exe, because moving a file is a rename rather than a copy. On at least one volume Windows satisfied that rename by copying and leaving the original behind. The update now deletes the staged file explicitly once the swap succeeds, rather than assuming the move consumed it.

If you are on v1.5.1 and have a `.update-*.part` file next to your exe, this build removes it on the next launch.

## Everything else is the same app

No changes to how clips are made. This is worth taking if you plan to keep updating — which, from v1.5.0 onward, you do not have to think about.

## For anyone reading the code

The documentation now covers the updater properly: what makes replacing a running executable possible on Windows, why the ordering is what guarantees a failed update leaves you with a working app, why cleanup has to retry rather than delete once, and what a checksum published by the same server that serves the file does and does not prove.

The screenshots were also retaken — the ones in the README predated the launch card, the version display and the update button.
