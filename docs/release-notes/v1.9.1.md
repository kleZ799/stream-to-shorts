When a clip fails to render, the app now tells you why.

## The log said a number and nothing else

Someone ran a video through and every clip failed. The whole explanation their
log offered was this:

> Command '[...]' returned non-zero exit status 3752568763.

That is not a helpful sentence, and it is not even really an exit code. ffmpeg
reports failures with its own error numbers, which Windows then hands back as
one enormous positive integer. Decoded, that one means *a library ffmpeg
depends on has failed* — during an encode, the video encoder itself.

The actual reason had already been written down. ffmpeg prints one line saying
what went wrong, and the app was quietly throwing it away: a windowed app has
no console window, so anything a background program prints goes nowhere. Every
failure looked exactly the same from the outside, whatever caused it.

Now the log carries what ffmpeg actually said — the encoder's own words about
the file it choked on — followed by a plain-English reading of the number. That
covers the ordinary ones too, so a full disk now says *No space left on device*
instead of `4294967268`.

This does not make a failing clip succeed. It makes a failing clip
**reportable**: paste the log into an issue and there is finally something in
it to act on.

## It also says which layout it actually used

The app decides per clip whether it can find your webcam. If it cannot, it
falls back to a plain centre crop — a reasonable thing to do, and something you
would want to know about.

It was announced *after* the clip finished, which meant a clip that failed
never announced it at all. The log went straight from "webcam on top" to a
failure, with no hint that it had given up on finding the webcam several
seconds earlier. It is said up front now, before the render starts.

That also fixes a small lie in the progress bar, which could mistake the
webcam's detection score for a count of finished clips and jump ahead of
itself.
