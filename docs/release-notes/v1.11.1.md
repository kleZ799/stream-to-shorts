A run that hits a snag now tries again instead of giving up.

## Every stage tries again by itself

A long video is forty minutes of work, and the things that break it rarely
break twice: a download that times out, a transcription that runs out of
memory once, a clip whose render trips over a file Windows has not let go of.
Until now any one of those ended the run.

Now the download, the transcription and the ranking each get three tries, a
few seconds apart, and every clip that fails to render gets tries of its own
while the rest carry on. Each retry is written in the log with the reason, so
you can see what happened.

Some errors cannot be fixed by waiting — a wrong API key, a used-up daily
quota, a private video, a file that is not there. Those fail straight away
rather than keeping you waiting for the same message three times.

## And when it still fails, you can send it round again

A run that fails shows **Try again**. It picks up where it stopped: the video
is already downloaded, the transcript is already saved, the ranking is saved
chunk by chunk, so nothing that finished is done twice. Fix whatever it was —
a key, a connection, some disk space — and press it.

A run that finished with a clip missing shows **Retry failed clips**, which
renders just those and puts them back where they belong, named after their
titles.

## The release itself is sturdier

v1.11.0's Linux build failed because the site its ffmpeg comes from answered
for a moment with an error page instead of the file. Every build now checks
that what it downloaded really is an archive, and fetches it again if not —
on Windows, macOS and Linux alike.

---

**StreamToShorts.exe** — about 220 MB, Windows, self-contained. Unsigned, so
SmartScreen will warn: **More info → Run anyway**.

**StreamToShorts-linux-x86_64** — about 278 MB, x86-64, self-contained, glibc
2.35 or newer. `chmod +x` it and run it. **Still untested on a desktop
distribution** — every published build is started by the release workflow and
asked for its interface before the release exists, but nobody has yet sat at
Fedora and made a Short with it. Take `StreamToShorts-linux-README.txt` too.

**StreamToShorts-macOS-arm64.zip** — about 165 MB, Apple Silicon only. **Still
a beta, and still has never been run on a Mac** — I do not own one, so it is
built and checked by GitHub's macOS runners and published without a human
opening it. Nothing in this release is platform-specific. If it does not
start, that is a bug here: `~/Movies/StreamToShorts/app.log` and
[an issue](https://github.com/kleZ799/stream-to-shorts/issues/new) are how it
gets fixed.

On v1.5.0 or later on Windows, or on any Linux build? The app will offer this
to you.
