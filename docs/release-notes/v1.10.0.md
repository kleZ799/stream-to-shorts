Stream to Shorts runs on Linux now, and it tells you when a render has finished.

## It runs on Linux

There is a third download: `StreamToShorts-linux-x86_64`. One file — `chmod +x`
it and run it. ffmpeg is inside, statically linked, so there is nothing to
install, and it updates itself from then on exactly like the Windows build
does.

Two things differ from Windows, and both are worth knowing before you start.

**It opens your browser rather than a window of its own.** Windows carries a
webview in the operating system and so does macOS. Linux carries neither, and
the one that exists here — WebKit2GTK — cannot be bundled and carried: it
renders pages in a separate process that it locates by a path compiled in when
*your* distribution built it, so a bundled copy opens a window that stays
blank. A working browser beats a blank window. Running from source, with
`python3-gi` installed, still gets you a real window.

**Transcribing runs on the CPU**, as it does on a Mac. The CUDA libraries would
unpack somewhere the dynamic linker was never told about, and a process cannot
add to its own library path once it has started — so bundling them would add
two gigabytes that nothing could load.

It needs glibc 2.35 or newer: Ubuntu 22.04, Debian 12, Fedora 36, and anything
after them. That floor is chosen rather than inherited — the build happens
inside an Ubuntu 22.04 container, and refuses to publish anything asking for
more.

**Nobody has run this on a desktop distribution yet.** It is built and
exercised under WSL, and every published build is started by the release
workflow and asked for its interface before the release exists — so it does
unpack, import, bind a port and serve you the app. That is not the same thing
as a full render on Fedora. If it goes wrong, that is a bug here rather than
something you did, and I would like to hear about it.

## It tells you when it's finished

A three-hour VOD is tens of minutes of work. Nobody sits and watches that, so
the window ends up behind a game or minimised — and until now the only way to
learn the clips existed was to go back and look. A run that finished at 2am was
found at nine.

It raises a desktop notification when a run ends now: a toast on Windows,
Notification Centre on a Mac, and whatever your desktop uses on Linux. Runs
that failed say so too, and name what went wrong.

When you are actually looking at the app it stays quiet, because a notification
for something already on your screen is only noise. It works out which by
asking the page, every twenty seconds, whether it is really on screen — so a
window you closed stops answering, which is the same answer.

On Linux this needs `notify-send` (from `libnotify-bin`) or KDE's `kdialog`.
Most desktops already have one. With neither, the app writes a line in its log
and carries on.

---

**StreamToShorts.exe** — 219 MB, Windows, self-contained. Unsigned, so
SmartScreen will warn: **More info → Run anyway**.

**StreamToShorts-linux-x86_64** — 278 MB, x86-64, self-contained, glibc 2.35
or newer. `chmod +x` it and run it. **Untested on a desktop distribution**, as
above. `StreamToShorts-linux-README.txt` beside it has the whole thing written
out, including the one library that is not in the box.

**StreamToShorts-macOS-arm64.zip** — 165 MB, Apple Silicon only. Unzips to a
folder with the app and `READ ME FIRST.txt`, which explains the first launch
macOS is about to refuse. **Still a beta, and still has never been run on a
Mac** — I do not own one, so it is
built and checked by GitHub's macOS runners and published without a human
opening it. If it does not start, that is a bug here:
`~/Movies/StreamToShorts/app.log` and
[an issue](https://github.com/kleZ799/stream-to-shorts/issues/new) are how it
gets fixed.

On v1.5.0 or later on Windows? The app will offer this to you. Linux builds
will offer it to each other from this release onward.
